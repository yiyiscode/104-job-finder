104 每日職缺日報 · 踩坑與決策紀錄 · 2026-08-22

Job Finder 系統指南

這份文件不介紹功能,而是記錄遇到了什麼、錯在哪裡、為什麼最後這樣選。 因為這個專案最貴的成本不是寫程式,是把架構前提搞錯了兩次 —— 而且兩次的方向還是相反的。

最重要的一句話:104 的 Cloudflare 是「看 IP 信譽」的,不是「有」或「沒有」。

台灣住宅 IP 被放行到 origin(那裡才輪到 Referer 白名單把關); AWS 資料中心 IP 在碰到 origin 之前就被 Cloudflare 攔下。 這就是為什麼這個系統最後跑在你自己的電腦上,而不是雲端。

一、現在長什麼樣

Windows 工作排程器每天 08:00 觸發,整趟約一分半,只有兩個步驟會碰到 104。

為什麼跑在本機而不是雲端

不是偷懶,是雲端兩種模式都實測過不了:

從哪裡方式結果
Modal(AWS 雪梨 52.63.49.208)純 HTTP403 · cf-mitigated: challenge · Just a moment...
Modal(同上)Patchright 真實瀏覽器更糟 —— 首頁直接跳 Turnstile 互動挑戰,程式無法自動通過
家用台灣住宅 IP純 HTTP✅ 連續 19 個請求全 200,Cloudflare 連挑戰都沒出

用真實瀏覽器反而被升級成互動挑戰 —— 這說明問題不在「怎麼發請求」, 而在 AWS 資料中心 IP 本身就被 104 的 Cloudflare 歸類為高風險訪客。換做法繞不過去。

modal_app.py 與整套瀏覽器程式碼完整保留。 哪天接了台灣住宅代理(填 config.yaml 的 scrape.proxy)就能切回雲端。 在那之前不要跑 modal deploy —— cron 會每天失敗, 把熔斷器燒到需要人工解除。

二、資料怎麼流

從 104 的一頁 JSON 到手機上的一則訊息。中間資料量收斂了兩百倍。

直覺上這應該是 爬蟲 → 存入 DB → AI 評分 → 發送 四步。 實際上爬蟲有兩次,而第二次夾在兩個 AI 階段中間 —— 詳細頁只抓粗篩活下來的那幾筆。這是整條流程最不直覺、也最關鍵的一個安排。

為什麼詳細頁要等粗篩之後才抓

因為兩道過濾各砍掉一個數量級,而詳細頁的請求數直接跟著最後那個數字走: DB 去重把 305 砍成 16(只留今天新出現的),粗篩再把 16 砍成 7。

如果這樣做詳細頁請求數結果
對抓到的每一筆都抓詳細頁305第 25 筆就撞上 max_details_per_run,整趟中止
只去重,不粗篩16總共 32 次,勉強過關但貼著上限 —— 職缺一多就爆
現在的做法7總共 23 次,離上限還有一半空間

所以粗篩不只是省 LLM 錢,它本身就是一道請求數的護欄。 把它拿掉,省下的是幾毛錢,付出的是撞上硬上限、抓一半就停。

兩支 API 各拿到什麼

API什麼時候打拿到什麼
/jobs/search/api/jobs
搜尋列表		 每組關鍵字、每頁各一次 jobNo、標題、公司、地區、salaryLow/High + s10、period、optionEdu、tags、description 摘要、link.job
Referer 要是搜尋頁
/job/ajax/content/{detail_id}
職缺詳細		 只對粗篩通過的那幾筆 完整職務說明、condition.edu / workExp(已經是文字,不用查代碼表)、jobDetail.salary(組好的字串)、jobCategory
Referer 要是該職缺自己的頁面

為什麼列表不夠用:列表裡的 description 看起來像 JD,但它中位數只有 123 字, 與 descSnippet 同源 —— 是摘要不是全文。想判斷技術棧與年資要求,詳細頁省不掉。

DB 存了什麼

四張表。最重要的觀念是:jobs 存的是「看過的每一則」,不是「達標的那幾則」 —— 因為它的主要用途是去重的判準,不是儲存結果。只存達標的,明天再看到同一則時就無從判斷看過沒有。

jobs — 每則職缺一列(目前 320 列)

什麼時候寫
抓到就寫,不管有沒有達標。推播成功後再回寫 status。
值得注意的欄位
last_new_at 上次被判定為「新」的時間 —— 重新上架的冷卻期以它為基準, 擋掉雇主天天刷新上架日就天天被推播; content_hash 分辨「內容真的改了」與「只是刷新上架日」; raw_summary / raw_detail 原始 JSON; status 是 new / screened_out / scored / notified。
為什麼留原始 JSON
這本身就是防封鎖策略的一部分 —— 調 prompt 時 --replay 完全不必再碰 104,104 改版時也能直接 diff 新舊結構。

scores — 每次深評一列(目前 10 列)

什麼時候寫
深評完成當下,逐筆寫入。粗篩的結果不進這張表,只反映在 jobs.status。
值得注意的欄位
adjustments 記下程式端套用了哪些修正(算術幻覺、verdict 降級、年資 hard rule)—— 這是唯一能看出模型錯在哪的地方; total_score 是程式重算過的,不是模型自己加的; raw_response 留著模型原始輸出,換模型時可以直接比。
為什麼分開存
同一則職缺可能被評很多次(重新上架、--replay)。放在 jobs 裡會被覆蓋掉,就看不出評分隨模型版本的漂移。

runs — 每次執行一列(目前 4 列)

什麼時候寫
開跑時建列,結束時補齊 —— 被護欄擋下的執行也會寫,不然看不出「今天到底跑了沒」。
值得注意的欄位
requests_used 是稽核欄位:這個數字失控就代表護欄有漏洞; schema_drift_count 是 104 改版的早期警訊; status 分 success / partial / blocked / failed / skipped, blocked 與 failed 的處置完全不同。
還有一個用途
「今天已經執行過」這道護欄就是查這張表 —— 所以開機後補跑不會重複推播。

circuit_state — 熔斷器,永遠只有一列

怎麼保證只有一列
schema 直接寫死 CHECK (id = 1)。熔斷器有兩份狀態是災難:一份說可以跑、一份說在冷卻。
值得注意的欄位
consecutive_failures 決定冷卻多久 —— 24h → 72h → 無限期(需手動解除); tripped_at 是冷卻計時的起點;reason 留著當時的判斷依據。
為什麼放 DB
它必須跨執行存活。放記憶體的話,排程每天起一個新行程,熔斷器等於不存在。

一個容易忽略的順序問題:狀態是「推播成功之後」才回寫的。

如果先標記 notified 再送 Telegram,送失敗就會變成「標記說推過了,但你根本沒收到」—— 而且因為標記已寫,明天也不會再推,那則職缺就永久消失了。 所以順序刻意是先送、後標記、再存檔。

三、三次轉向

架構前提被推翻兩次,方向相反。這一段是全文最值得讀的部分。

01
起點 · 判斷錯誤

「104 有 Cloudflare,必須用真實瀏覽器」

當時的證據
用 WebFetch 打 /jobs/search/api/jobs,得到 403 加上「Enable JavaScript and cookies」。
錯在哪
那個管道有兩個問題同時存在,而它們被混為一談了:設不了 Referer header,而且從資料中心出去。看到 403 就直接歸因給 Cloudflare。
代價
整套架構圍繞 Patchright、warmup、Chrome profile 打包、cf_clearance 綁 IP 的處理打轉。還把「Modal 的 IP 過不了 Cloudflare」列為專案唯一的存亡點。
02
更正 · 方向對,結論太武斷

「104 根本沒有 Cloudflare,只有 Referer 白名單」

怎麼發現
使用者問「能不能不用手動操作瀏覽器」,才回頭用 curl 親自測。不帶 Referer → 403 且 body 是 0 bytes(不是挑戰頁);加上 Referer → 200、117 KB JSON、1.2 秒。
做了什麼
整個抓取層改成純 httpx。image 從幾百 MB 降到幾 MB、記憶體 4 GB 降到 512 MB、單次請求從十幾秒降到 1.2 秒。
錯在哪
只在一個 IP 上驗證,就推論成通則。還信心滿滿地宣告「modal run 不再是存亡點了」—— 把前一份計畫裡唯一標紅的風險親手劃掉。
意外收穫
真實回應到手,才發現 normalize.py 的欄位對應錯得比預期多(見下一節)。這些錯誤在瀏覽器架構下永遠不會被發現,因為 fixture 是我手工編的。
03
現在的理解

Cloudflare 依 IP 信譽 觸發,兩件事同時為真

怎麼發現
部署前的驗證跑,第一個請求就 403。寫了一個 diagnose() 從 Modal 發一個請求把回應攤開:egress IP 52.63.49.208(AWS 雪梨)、server: cloudflare、cf-mitigated: challenge。
正確理解
信譽夠的 IP 被放行到 origin,在那裡才遇到 Referer 白名單;信譽不夠的 IP 在碰到 origin 之前就被攔下。所以第 1 次和第 2 次的觀察都是真的,只是各自只看到一半。
連瀏覽器也不行
切到 Patchright 再試,首頁直接跳 Turnstile 互動挑戰 —— 比純 HTTP 拿到的 Managed Challenge 更嚴重,代表這個 IP 已被歸類為高風險訪客。
最終決定
改用 Windows 工作排程器跑在本機。這也推翻了我原本的風險排序 —— 當初把「搬回本機」列為最後手段,理由是「把風險轉嫁到家用 IP」,但那個排序建立在「雲端可行」的前提上。

從這三次學到的

用什麼工具查證,會決定你查到什麼

問題
WebFetch 設不了 header。它拿到的 403 根本回答不了「這個端點需要什麼 header」 —— 卻被當成了答案。
現在怎麼防
凡是要判斷「為什麼被擋」,一律用能完整控制 request 的工具(curl / httpx),而且把回應完整印出來,不只看狀態碼。

單一環境的觀察不能當通則

問題
第 2 次更正時,19 個請求全 200 的證據非常有說服力 —— 但那全部來自同一個 IP。
現在怎麼防
diagnose() 留在 modal_app.py 裡。任何「本機好好的、雲端壞掉」都能一次看出 egress IP 與 cf-mitigated,不用再猜。

四、坑 · 104 的資料

每一條都是拿到真實回應才發現的。手工編的 fixture 一條都測不出來。

jobNo 與 detail_id 是兩個不同的 ID

症狀
詳細頁 100% 回 404「職務不存在」。
根因
同一則職缺 jobNo=15305872,但連結是 /job/94234。詳細頁 API 只吃連結尾段。
修法
領域模型拆成兩個欄位:job_no(去重主鍵)與 detail_id(打 API 用)。fixture 檔名也改用 detail_id,免得養出「本機會過、上線就 404」的假象。

s10 是薪資類型,不看就會寫出「月薪 56 萬」

症狀
日報上出現「月薪 567,000~675,000 元」的醫療 AI 工程師。
根因
那是年薪。s10(混淆過的欄位名,等同詳細頁的 salaryType):10=面議 50=月薪 60=年薪。三筆樣本交叉驗證完全吻合。
修法
薪資字串依類型組合,另加 monthly_equivalent() 換算 —— 否則「月薪 45K 以上」這種判斷會讓每個年薪職缺都不當過關。

data 本身就是陣列

症狀
解析出 0 筆職缺。
根因
沒有 data.list;總數在 metadata.pagination.total / .lastPage。
修法
照真實結構重寫,並保留原本的 schema drift 記錄機制 —— 那套設計是對的,只是餵錯結構。

description 含換行,打散批次 prompt

症狀
粗篩靠「每筆固定四行」讓模型分辨筆與筆的邊界,一次 15 筆時會張冠李戴。
根因
摘要文字本身有換行,直接塞進 prompt 就破壞了結構。
修法
to_screen_block() 進 prompt 前把空白壓成單行。有測試釘住行數。

tags 是 dict,退回 param 會撈出內部代碼

症狀
職缺標籤出現 wf1、wf2、wf7。
根因
desc 為空時退回 param,而 param 是 104 的內部代碼。
修法
只取有內容的 desc,空的直接略過 —— 放進 prompt 只是噪音。

搜尋參數本身就寫錯了(原始需求裡的)

症狀
jobexp=3 以為是「3 年以下」,實際是「1~3 年」這個級距 —— 會漏掉所有「1年以下 / 經歷不拘」的缺。
還有
order=15 是符合度排序不是日期,而且改版後數值會漂移。
修法
改送 jobexp=1,3;完全不用 order,新鮮度靠 isnew + appearDate + DB 去重。config.py 會擋下 jobexp=['3'] 這種寫法。

一個好消息:period 是實際要求年資的「數字」,不是級距代碼。

送 jobexp=1,3 回傳 0/2/3,送 jobexp=10 回傳 6~9 —— 交叉驗證確認。 所以年資 hard rule 可以直接讀整數,不必對中文跑正規表達式,可靠度大幅提升。

五、坑 · 我自己寫的

這幾個的共通點是:測試全綠,但實際用起來壞掉。

測試通過,卻真的送出 6 次 Telegram 訊息

症狀
使用者收到 6 份一模一樣的測試訊息。
根因
我加了一個煙霧測試檢查每個腳本的 --help 能不能跑完。但 send_test_message.py 沒有 argparse —— 它會忽略 --help、把整個腳本跑一遍、然後正常結束。exit code 一樣是 0,所以測試「通過」了。
修法
所有腳本補上 argparse;測試改成必須驗 stdout 有 usage: —— 那才證明是 argparse 處理的,而不是腳本真的跑了一遍。

--replay 被去重擋掉,整個旗標作廢

症狀
重播舊資料調 prompt,深評 0 筆。
根因
重播的職缺當然「看過了」,去重把它們全部濾掉。而 --replay 存在的唯一理由就是重跑已看過的資料。
修法
離線模式自動開 rescore_all,跳過去重但仍寫進 DB(否則外鍵掛不上、之後也無法再 replay)。正式排程走預設路徑,去重照常。

暖容器把已刪掉的狀態復活

症狀
刪掉 local_data/ 重跑,結果還是說「今天已經執行過」。
根因
Database.open() 只在倉庫端有檔案時才複製,沒清本地殘留 —— 於是沿用了上次跑剩的 DB。在 Modal 上就是暖容器把已刪除的熔斷紀錄復活。
修法
開檔前一律先 unlink(missing_ok=True)。

fixture 輪流套 detail,讓預覽分數全是假的

症狀
「8 年以上、需帶團隊」的資深缺拿到 96 分。
根因
fixture source 把幾份 detail 輪流套到每個職缺上,結果資深缺配到「經歷不拘」的詳細頁。
修法
改成嚴格按 detail_id 對應,對不到就不給 detail。評分端本來就有「沒有詳細內容時保守評估」的路徑,走那條才誠實。

相對路徑讓 Modal 容器 crash-loop

症狀
容器反覆啟動失敗,FileNotFoundError: 'config/config.yaml'。
根因
modal_app.py 在本機與容器裡都會被 import:本機為了定義 app,容器為了跑函式。兩邊的設定檔位置不同。
修法
兩個路徑都試,都找不到才退回預設值。

護欄自己誤判:設定錯誤被當成「被封鎖」

症狀
Referer 掉了會讓熔斷器啟動,系統白白停機 24 小時 —— 而冷卻之後設定還是錯的。
根因
兩種 403 長得完全不一樣,但原本一律當成封鎖。
修法
classify_403():body 空 = 我方設定問題(告警但不熔斷),body 有挑戰頁特徵 = 真被擋(熔斷)。瀏覽器路徑讀 body 可能失敗,所以 detect_block() 對 403 維持 fail-closed。

六、坑 · LLM 的行為

便宜模型的問題不是「笨」,是不照格式走。而格式正是我們拿來做防幻覺交叉驗證的東西。

問題實測修法
模型自己發明 verdict 值 22 筆裡有 9 筆吐出 worth_a_shot、worth_a_try —— prompt 裡從沒出現過的字 JSON schema 加 enum 約束(改用 Literal)→ 降到 0 筆
無效 verdict 被當成負面訊號 無法對應時回 "maybe",而 maybe 會觸發降級 —— 一個 75 分的職缺因此掉到 68 分消失 改成回 None 並跳過交叉驗證。用字不合格不代表模型認為職缺不好
門檻頂到每日上限 單一關鍵字的 32 筆裡,70 分就有 10 則達標(正好是上限)。而正式跑有六組關鍵字 門檻 → 80。分佈上 70–79 與 80+ 之間有明顯斷層
「待遇面議」被當成缺點 22 筆裡 19 筆是面議,practical_fit 幾乎變成常數,失去鑑別力 prompt 明講面議給中間值 5–6 分。台灣八成職缺不揭露薪資,拿它扣分等於懲罰八成的職缺
把新鮮人當成資深工程師 看到滿滿的 BERT / YOLO / RAG 專案,就給「要求 8 年、需帶團隊」的職缺高 exp_fit 程式端 hard rule:要求 ≥ 5 年就把 exp_fit 夾到 8 並重算。現在直接讀 period 整數,比解析中文可靠

共通的原則:能用規則做的事就用規則做。 總分程式端重算(不信模型的加法)、verdict 交叉驗證、年資 hard rule —— 三道校正全都是純函式,所以可以被完整測試,而且不會因為模型換版而漂移。

七、關鍵決策

每個決策附上被否決的選項 —— 那通常比「選了什麼」更能說明理由。

ports.py 的三個 Protocol

選了什麼
JobSource / Scorer / Notifier 三個介面,pipeline 只認介面不認實作。
為什麼
當初寫的理由是「風險備案」。結果它真的付了錢:抓取方式從真實瀏覽器整個換成純 HTTP,而 pipeline.py、storage/、scoring/、notify/ 一行都沒改。
否決了什麼
直接在 pipeline 裡呼叫 Playwright。那樣的話第 2 次轉向就是整個重寫,而不是換一個實作。

護欄先於功能:RequestBudget.acquire() 是唯一入口

選了什麼
所有對 104 的請求都必須先過同一個守門員:路徑黑名單 → 預算檢查 → 強制節流 → 計數。
為什麼
節流如果靠「呼叫端記得 sleep」,遲早會有人忘記。做成唯一入口就不可能繞過。換成 HTTP 模式時特地把它抽成兩條路共用,而不是各寫一份。
否決了什麼
在每個抓取函式裡各自 asyncio.sleep()。也否決了「HTTP 模式比較輕所以放寬節流」—— 節流是對 104 的禮貌,跟我們這邊輕不輕沒關係。

零重試 + 熔斷器

選了什麼
偵測到封鎖訊號立刻中止整趟,熔斷 24h → 72h → 需手動解除。連 Modal 的 function 級重試也關掉(retries=0)。
為什麼
重試是把「暫時被挑戰」變成「永久封 IP」的頭號原因。如果 104 已經在擋你,隔天 08:00 再自動跑一次只會坐實「這個 IP 是機器人」。
實際救了什麼
Modal 那兩次驗證跑,各自只發了 1 個請求就退場。護欄表現無可挑剔。
否決了什麼
指數退避重試。對 403 / 429 來說,退避重試只是把同一個錯誤重複犯得比較慢。

絕不登入 104 帳號

選了什麼
設定檔連帳密欄位都沒有(出現 password 之類的鍵直接拒絕啟動);每次執行前掃 cookie jar 確認匿名。
為什麼
目標資料對未登入訪客完全開放,登入拿不到任何額外欄位 —— 只有壞處沒有好處。而 IP 被鎖可以換網路,帳號被停權就沒得救了。
額外收穫
HTTP 模式下這條變成天然成立 —— 我們根本不送任何 cookie。

兩階段評分,粗篩必須批次

選了什麼
粗篩一次帶 15 筆(只用列表欄位),深評逐筆(帶完整 JD)。
為什麼
履歷放進 prompt 約 800 token,是每次呼叫的固定成本。批次攤提後每筆邊際成本只剩約 60 token;逐筆粗篩等於把履歷付了 15 次。
否決了什麼
批次超過 15 筆 —— 實測會出現漏回 job_no 與後段被前段錨定。所以批次後必須驗集合,缺的自動補一輪。

保留原始 JSON

選了什麼
每次抓到的 raw JSON 存進 jobs.raw_summary / raw_detail,模型的原始輸出存進 scores.raw_response。
為什麼
這本身就是防封鎖策略的一部分 —— 調 prompt 時 --replay 完全不需要再碰 104。104 改版時也能直接 diff 新舊結構。

Telegram 用 HTML 而不是 MarkdownV2

為什麼
MarkdownV2 要跳脫 18 個字元,而職缺標題與薪資裡到處是 ( ) - .,漏一個就整則 400。HTML 只要跳脫 & < > 三個。
額外保險
400 時降級成純文字重送一次 —— 標題偶爾有怪字元,寧可醜也不要整則消失。

User-Agent 誠實標示,不偽裝

選了什麼
JobFinder/0.1 (personal job-seeking daily digest; +email)。含 Mozilla 會被 config.py 拒絕啟動。
為什麼
104 的 API 根本不檢查 UA(實測 curl/8.x 也照樣 200)。既然偽裝沒有任何好處,誠實標示反而降低合規風險,也讓 104 想聯絡時有管道。
注意例外
瀏覽器模式完全不讀這個欄位 —— 那邊一律用 Chromium 自己的真實 UA,因為偽造的 UA 與實際指紋不一致才是最明顯的機器人訊號。

八、日常操作

程式面已經完成。這一段是你之後真的會用到的東西。

收到訊息時怎麼判斷

你收到的意思該做什麼
摘要 + 幾張卡片一切正常看職缺
「今天沒有新職缺」正常。104 當天沒新缺,或新缺都看過了什麼都不用做
「403 但這是設定問題不是被封鎖」body 空的 403 = Referer 掉了檢查 scrape.referer。熔斷器沒啟動,修好就能跑
「104 抓取被中止」真的被擋了,熔斷器已啟動不要手動重跑。家用 IP 被擋是嚴重訊號,先停幾天
摘要帶 schema drift 警告104 可能改版了跑 pytest tests/test_normalize.py 看哪些欄位對不上
什麼都沒收到電腦沒開機,或排程沒跑看 local_data\daily.log 的尾巴

指令

# 開發:完全不碰 104,可以反覆跑(fixture 是真實回應)
jobfinder run --from-fixtures --fake-llm --dry-run   # 零成本,看排版
jobfinder run --from-fixtures --dry-run              # 用真 LLM 調 prompt
jobfinder run --replay 42                            # 拿舊資料重跑評分
jobfinder status                                    # 執行紀錄 + 熔斷器 + 請求量稽核

# 排程
Start-ScheduledTask -TaskName "JobFinder Daily"       # 手動觸發一次
Get-Content local_data\daily.log -Tail 40 -Encoding UTF8   # 排程紀錄(少了 -Encoding 會亂碼)

# 會連 104 —— 一次性的,不要反覆跑
jobfinder run --limit 5                              # 端到端冒煙,約 6 秒

改東西時

你想做的該改哪裡
加關鍵字、調門檻、換模型只改 config/config.yaml
104 改了 API 路徑改 scrape.search_api_pattern,不用動程式
加新的抓取行為一定要走 RequestBudget.acquire(),不要自己發請求
新增 scripts/ 底下的腳本一定要有 argparse —— tests/test_scripts.py 會驗 --help 印得出 usage:
想放寬硬上限config.py 會直接拒絕啟動。要改必須先在 CLAUDE.md 說明理由

緊急剎車

把 .env 的 JOBFINDER_SCRAPE_DISABLED 改成 1, 下次排程就會直接短路,一個請求都不發。 或把 config.yaml 的 scrape.enabled 改成 false。 兩者都立即生效,不需要重新部署任何東西 —— 這是跑在本機的好處之一。
