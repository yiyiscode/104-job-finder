# Streamlit Web UI 規格（2026-09-24）

**只講 Web UI。** 其餘優化方向見 `docs/handoff-2026-09-23.md`，決策來源見 `D:\Career\decisions.md` D21。

---

## 一、目標

現況的輸出是 **Telegram 卡片流**——那是推播介面，不是決策介面：不能排序、不能比較、不能標記「已看過／不投」。

使用者的求職 SOP 是**週一選、週五投**（`D:\Career\applications\job-target-list.md`）：

> 週一：跑 Job Finder → 候選清單 → 套三道篩選 → **選定本週 4 家（這天不投）**
> 週二–週四：逐條比對＋改客製自傳段
> 週五：投遞＋記錄

**這個 UI 要服務的就是「週一」那一小時**，外加一個把累積資料變成分析產出的頁面。

**兩個動機**（使用者自述）：①週一選家不好用 ②面試可以 demo。

**它不是新專案**，是把兩個既有項目接上介面：候選清單頁 = 規則層過濾的輸出層；技能趨勢頁 = 原本就在 10 週計畫裡的「分析副產品」。

## 二、篩選條件（候選清單頁要實作的）

三道閘門，**依序**由便宜到貴。UI 要讓使用者看得出每一筆卡在哪一道。

### 第 1 道：硬門檻（結構化欄位，程式全自動判定）

| 條件 | 判定方式 | 不通過 |
|---|---|---|
| **公司人數 ≥ 30** | `jobs.raw_summary` 的員工數欄位；「暫不提供」視為**未知不排除**，標黃 | ❌ 排除 |
| **地點：台中以北** | `area_desc`。台北／新北／桃園／新竹縣市／苗栗／台中皆可；**高雄、台南、嘉義、雲林、彰化排除** | ❌ 排除 |
| **不輪班** | JD 全文（`raw_detail`，無則用 `raw_summary`）含 `輪班`／`on-call`／`夜班`／`中班` | ❌ 排除 |
| **非派遣** | 公司名或產業含 `派遣`／`人力仲介` | ❌ 排除 |
| **非實習／工讀** | 職稱含 `實習`／`intern`／`工讀`／`時薪` | ❌ 排除 |
| **非校園徵才／預聘** | 職稱含 `校園徵才`／`預聘`／`研發替代役`。**例外：含「秋季」者保留** | ❌ 排除 |
| **避開 AI 職稱** | 職稱含 `AI 工程師`／`人工智慧工程師`／`演算法工程師`（`decisions.md` D7） | ⚠️ 標紅但**不排除**，讓使用者自己判斷 |

**薪資規則**（95% 面議，不能當硬門檻用）：

- `salary_high` 有值且 **< 50,000** → ❌ 排除（明確低於底線且無上調空間）
- `salary_low` 有值且 **< 50,000**，`salary_high` 為空（「以上」型）→ ⚠️ 標黃，備註「談薪時 5 萬不可退」
- 面議 → 不排除，標為未知

**學歷不篩。** 使用者有碩士（臺科大資訊管理研究所 M.S.），`38% 只收碩士` 對他不構成門檻。只需**顯示**學歷欄供參考。

**經歷**：`不拘` 與 `1 年以上` 都算可投（jr 定義），`2 年以上` 排除。

## 三、Web UI 要的功能（只有這些）

### 頁 1：候選清單（週一用）

**資料源**：`jobs` LEFT JOIN `scores`，只讀不寫抓取相關的東西。

**欄位**：公司 ｜ 職稱 ｜ 地點 ｜ 員工數 ｜ 經歷 ｜ 學歷 ｜ 薪資 ｜ 英文要求 ｜ 深評分數 ｜ 命中率 ｜ 104 連結（可點）

**三道閘門的視覺化**：每一筆顯示三個狀態燈，**看得出卡在哪一道**。硬門檻自動判定；閘門②③ 若 LLM 未跑則顯示「未判定」。

**排序**：深評分數 ｜ 首次出現日期 ｜ 員工數 ｜ 命中率

**篩選**：
- 產業格（半導體／金融／軟體，依 `cust_name` 或 104 產業別）
- 是否要求英文（使用者的即席口說是弱項，**不要求英文的優先**）
- 通過第幾道閘門
- 日期區間（預設「本週新增」）

**標記**（寫回 SQLite，建議新增 `decisions` 表或在 `jobs` 加欄位）：
- 狀態：`投` ／ `不投` ／ `待確認`
- **不投時必填原因**（下拉）：`SI接案` ／ `無新人培訓` ／ `職務打雜` ／ `命中率不足` ／ `薪資低於底線` ／ `要求英文` ／ `其他`
- 備註（自由文字）

> **「不投原因」這個欄位很重要**——它是之後檢討「閘門有沒有設對」的唯一資料。如果三個月後發現 80% 都是因為同一個原因被刷掉，那條規則就要重看。

**匯出**：選定的 4 家可匯出成 Markdown 或 CSV，貼進投遞追蹤用。

### 頁 2：技能趨勢

| 圖 | 內容 |
|---|---|
| 技能頻率 | 技能關鍵字出現率排行。**摘要層與全文層分開兩張，不要合併** |
| 隨時間變化 | 以週為單位，看技能頻率有沒有移動 |
| 薪資分佈 | 有揭露者的下限／上限分佈 |
| 公司規模分佈 | 員工數分桶 |

**每張圖都必須標樣本數與偏誤說明。**

## 四、⚠️ 取樣偏誤（做技能趨勢前必讀）

2026-09-24 查 `local_data/jobs.db`（跨度 2026-08-21 → 09-24）：

| 欄位 | 筆數 | 覆蓋率 |
|---|---:|---:|
| 總職缺 | 1,721 | — |
| `raw_summary`（列表摘要） | 1,721 | 100% |
| **`raw_detail`（JD 全文）** | **369** | **21%** |
| 薪資下限 | 610 | 35% |
| 不重複公司 | 1,021 | — |

**那 369 筆不是隨機樣本，是「粗篩通過」的子集**——`max_details_per_run: 18` 加上 `rough_threshold: 45` 雙重限制，只有 LLM 粗篩過門檻的才去抓詳細頁。

**直接拿 `raw_detail` 算技能頻率會循環論證**：量到的是「跟使用者履歷匹配的職缺」的技能分布，不是市場分布。履歷上有的技能，在匹配職缺裡出現率當然高。

**處置**：
1. **摘要層（N=1,721）做母體估計、全文層（N=369）做細節，兩層分開報**
2. 每張圖標樣本數與偏誤來源
3. 薪資分佈標揭露率（35%），並註明「以上」型無上限，上限統計只算有明確上限者

> 這一條本身就是面試材料：發現自己的樣本有選擇偏誤、說得出為什麼、改了方法——那是統計本科該有的判斷，而且背不出來。

- **花俏視覺設計**——這是工作介面不是作品集網站
- **在 UI 裡觸發抓取**——見下

## 六、硬限制（違反會壞掉或把使用者的 IP 賠進去）

| # | 限制 | 出處 |
|---|---|---|
| 1 | **UI 只讀 DB，不要從 UI 觸發 104 抓取。** 抓取有請求預算、節流與熔斷三道護欄，UI 按鈕會繞過它們 | `src/jobfinder/scrape/budget.py` |
| 2 | `HARD_MAX_NAVIGATIONS_PER_RUN = 40` 是程式常數，設定檔調不動 | `src/jobfinder/config.py:22` |
| 3 | 被擋即零重試 → 熔斷（24h → 72h → 手動 reset）。**不要為了 UI 方便加 retry** | SPEC 規則 2 |
| 4 | 絕不登入 104；設定檔出現 `password`／`token` 類的鍵會拒絕啟動 | SPEC 硬性規則 9 |

**護欄有 61 個專屬測試。改動後 `pytest` 必須全過（目前 256 passed）。**

**寫回 DB 的部分**：標記功能會寫 SQLite，要確認不與 `pipeline.py` 的寫入衝突（同一個 db 檔）。建議獨立一張表、用短交易，不要在 pipeline 執行時開 UI 寫入。
