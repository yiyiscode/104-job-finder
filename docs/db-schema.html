Job Finder 資料庫圖解

四個 SQLite 檔各是什麼、誰在寫、彼此怎麼對得起來。數字是 2026-10-03 讀 local_data/ 副本統計的(jobs.db 檔案時間 12:02、decisions.db 12:39、hitrate.db 10/02 23:29、shortlist.db 09/28 17:55)。每一條說明後面標了對應的原始碼位置。

一句話版本

一個資料庫只給一個寫入者。每日 pipeline 寫 jobs.db、Web UI 寫 decisions.db、命中率排程寫 hitrate.db、投遞清單指令寫 shortlist.db。四個檔之間沒有外鍵,是程式讀取時用職缺編號把它們對起來的。

jobs.db

職缺主檔、評分、執行紀錄、熔斷器

寫入者:每日 pipeline(08:00)

decisions.db

你的投／不投、想去程度、週次、送出、已關閉

寫入者:Web UI

hitrate.db

第 3 道閘門「必備命中率」逐條判定

寫入者:jobfinder hitrate(排程在 pipeline 之後)

shortlist.db

手動匯入的投遞清單,與補抓的詳細頁

寫入者:jobfinder shortlist

為什麼要拆成四個檔

pipeline 不是在 jobs.db 上直接改,而是複製一份到暫存區操作,結束時整檔換名蓋回去(src/jobfinder/storage/db.py:206 os.replace)。這帶來兩個後果:

  • 別人寫進 jobs.db 的東西,會在 pipeline 蓋回檔案時消失。所以你的標記不能放在這裡。
  • Windows 上只要有程式開著 jobs.db,換名就會失敗,當天的資料與熔斷器狀態會靜靜遺失。所以 Web UI 只讀它的快照副本(src/jobfinder/webui/snapshot.py:16),從不直接開原檔。

完整理由見 ADR 0001。

全景圖

jobs.db 每日 pipeline

jobs — 職缺主檔(2,183 筆)

每一筆 104 職缺一列,job_no 是主鍵,也是去重的依據。列表的原始 JSON 存在 raw_summary;通過粗篩、抓過詳細頁的才有 raw_detail(目前 401 筆)。schema.sql:8 · 寫入 repo.py:39 register()

status 記的是 pipeline 對這筆的處理結果,跟你在 UI 的閘門無關:

status意思筆數
new已登記,還沒被評過131

scores — 評分紀錄(730 筆)

粗篩(stage='screen',47 筆)與深評(stage='deep',683 筆)都存,包含五個維度分數、一句話、亮點、紅旗、履歷建議與模型原始回應。同一筆職缺可以有多筆評分,UI 取最新的深評。schema.sql:64 · 寫入 repo.py:176 save_score()

  • job_no → jobs,ON DELETE CASCADE:職缺被清掉時,它的評分一起刪。
  • run_id → runs:記這筆是哪一次執行評的。沒有設刪除行為,所以清理舊 runs 時必須跳過還被引用的(見下方「清理」)。

runs — 每次執行的稽核(43 筆)

一次執行一列:抓了幾筆、新的幾筆、各關淘汰幾筆、對 104 發了幾個請求、LLM 花多少錢、錯誤類型。目前 success 40、skipped 2、partial 1。requests_used 失控就代表護欄有漏洞。schema.sql:42 · 寫入 repo.py:262 start_run()

circuit_state — 熔斷器(固定 1 列)

CHECK (id = 1) 保證全表只有一列。被 104 擋時改成 open,冷卻期內 pipeline 一個請求都不發。目前是 closed、連續失敗 0。schema.sql:90 · 寫入 repo.py:375 save_circuit()

清理(prune)

每次執行最後會刪掉 180 天沒再看到的職缺(評分跟著 CASCADE 刪)與 180 天前的 runs。還被 scores 引用的舊 runs 會留著 —— 職缺若一直被抓到,它的評分不會被刪,指向的那次執行一刪就會撞外鍵、讓整次執行出錯。這是 2026-10-03 修掉的問題(原本最早約 2027-02-18 會觸發)。repo.py:393 prune()

decisions.db Web UI

你在 UI 上做的每個決定。五張表共用同一套規則:src/jobfinder/webui/decisions.py

  • 只追加、不覆蓋。改判就是再新增一列,讀取時同一筆職缺取最後寫入的那列。所以「待確認 → 投」的軌跡都留著。
  • NULL 代表撤銷。週次、送出、已關閉這三張表的日期欄是 NULL 的那一列,意思是「取消先前那筆」。
  • 短交易。每次操作自己開連線、寫完就關,不長期佔著檔案。

跨檔怎麼對起來

四個檔之間沒有外鍵(SQLite 的外鍵也不能跨檔),全靠程式讀取時對應:

  1. 大部分用 job_no。decisions.db、hitrate.db 的 job_no 對到 jobs.db 的 jobs.job_no。
  2. 投遞清單時期的標記用 detail_id 存。目前 decisions 表 24 個職缺鍵裡,7 個是 job_no、17 個是 detail_id,沒有對不上的。讀取時程式先建一張「detail_id → job_no」對照表,把兩種鍵的紀錄合在一起、依寫入順序取最新 —— 不必搬資料。webui/candidates.py:91 detail_aliases() · decisions.py:162 latest(aliases)

沒有外鍵的代價:jobs.db 清掉某筆職缺後,decisions.db 裡它的標記不會跟著刪,只是 UI 找不到對應的職缺、不會顯示。這是刻意的:你的決定紀錄比職缺本身活得久。
